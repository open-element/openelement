# 1.0 Alpha final convergence audit

Date: 2026-09-11\
Candidate inspected: `a6444b7289072edd8162fe13b70cb45d16bc1eb2` on `dev`

## Executive decision

OpenElement is not yet at architecture-freeze quality.

The runtime and qualification work is strong enough to continue toward an Alpha, but the current
repository still has two kinds of unfinished convergence:

1. The public product doctrine says Element + Router while the published package surface still says
   Element + App + Adapter Vite + Create. (Resolved: the workspace now publishes exactly Element,
   Router, and Create; see "Package decisions" below.)
2. The repository has 74 tracked files under `tools/` (16,331 TypeScript lines), including active
   product qualification, generic build plumbing, obsolete v0.44 evidence machinery, duplicated
   consumer harnesses, and unreferenced experiments in one undifferentiated directory.

The correct next move is not a blind package merge or a blanket tools deletion. First correct public
ownership, then replace generic infrastructure where an upstream tool proves equivalent behavior,
then delete the displaced implementation in the same change.

The pre-1.0 GitHub Release objects are explicitly out of scope for this pass. They must not be
deleted, edited, or used as a reason to block the code and repository audit.

The actual published workspace is:

### Package decisions

- Rename `@openelement/app` to `@openelement/router` before the first public 1.0 Alpha. A permanent
  `app` package that merely distributes Router creates a second product name and makes the durable
  import path lie about ownership.
- Do not create `@openelement/cli`. `dev`, `build`, `start`, and `preview` are application lifecycle
  operations and belong to Router.
- Dissolve `@openelement/adapter-vite` as a public product. Its Element compiler plugin belongs at an
  explicit Element tooling subpath (implemented: the compiler, TSX lowering, Part Program, compiler
  diagnostics/source maps and the Vite transform now live in `@openelement/element` under the
  `./compiler` and `./vite` subpaths). Its routing, SSG, SSR, Nitro, and application lifecycle belong
  under Router tooling subpaths (implemented: the Vite plugin, dev/build/start/preview CLI, Nitro
  mount, and framework-mode fixtures now live in `@openelement/router` under `./src/vite/`,
  `./src/cli/`, and `./src/nitro-mount.ts`, exported via the `./vite`, `./nitro-mount`, `./cli/build`,
  and `./cli/start` subpaths; `packages/adapter-vite` is deleted and the workspace publishes exactly
  Element, Router, and Create).
- Keep Vite and host-only code out of browser entry points through subpath exports and optional peer
  dependencies. A large package is acceptable only when its internal dependency boundaries remain
  enforceable; a large undifferentiated module is not.
- Keep `@openelement/create` independent because it runs before an application has installed the
  framework. It must consume only public package names and versions.
- There is no evidence in the current repository for a real webpack, Rspack, or Deno adapter family.
  An adapter abstraction therefore creates hypothetical substitutability rather than useful
  polymorphism.

### Responsibility moves

Move from App to Router:

- route records, URL resolution, loaders, actions, method policy, redirects, and cancellation;
- request contexts, HTTP execution, document semantics, and browser navigation;
- Route Mode, Native Framework Mode, Lit Framework Mode, SSR, and renderer selection;
- public Router types and client-only projections.

Move from Adapter Vite to Router (implemented: all five items now live in
`packages/router/src/vite/`, `packages/router/src/cli/`, `packages/router/src/nitro-mount.ts`, and
`fixtures/router-*`):

- route discovery and generated route entries;
- application Vite configuration, dev-server lifecycle, build orchestration, SSG, and SSR;
- Nitro mount and server output;
- `dev`, `build`, `start`, and `preview` entry points;
- framework-mode fixtures and application asset policies.

Move from Adapter Vite to Element tooling:

- TSX/decorator parsing used by the Element compiler (implemented: `packages/element/src/internal/compiler/`);
- Part Program generation, diagnostics, compiler source maps, and compiler validation (implemented:
  `packages/element/src/internal/compiler/semantic-core/`, public subpath `@openelement/element/compiler`);
- the Vite transform hook that invokes the Element compiler (implemented: `compiledElementPlugin` via
  `@openelement/element/compiler` and the standalone `@openelement/element/vite` authoring plugin).

Do not move generic content collections, MDX, sitemap generation, or i18n into Router merely because
they currently live beside its build. Each needs a separate keep/remove decision based on a real
Alpha application. If it has no independent consumer, it should leave the core rather than enlarge
Router. (Decided during the Adapter Vite dissolution: generic content collections, blog data,
generated nav, sitemap generation, and the i18n build plugin had no consumer outside their own
tests and were removed with `packages/adapter-vite`; MDX route support was kept because the
static-only fixture's `app/routes/mdx-page.mdx` route is a real consumer pinned by the #954 build
contract tests.)

## Toolchain decisions

### Oxc: REJECT for the first Alpha compiler path

Oxc is capable of parsing TSX and exposes diagnostics, spans, transformation, and source maps. That
is not the missing evidence. The repository contains no executable Oxc experiment, representative
corpus result, malformed-input comparison, Part Program equivalence proof, or packed-consumer proof.
The tracked Oxc experiment is only an empty placeholder.

Adopting it now would introduce a second frontend immediately before architecture freeze. The first
Alpha should keep one production frontend: the TypeScript compiler API already used by the compiler.
Delete the empty Oxc experiment directory. Reconsider Oxc only after an independent benchmark and
semantic-equivalence proposal; do not carry two production frontends.

Oxc may later own generic parsing. It must never own Part Program semantics, OpenElement component
semantics, reactivity semantics, or the generated artifact contract.

### TypeScript 7: split decision

- CLI/typechecking: **ADOPT after a clean matrix run.** TypeScript 7 now ships as `typescript`/`tsc`,
  but the repository still pins TypeScript 5.9 while Deno 2.9 embeds TypeScript 6.0.3. First remove
  this three-version ambiguity.
- Declaration emit: **DEFER until packed declarations and API snapshots are equivalent.** The
  package boundary is more important than toolchain novelty.
- Compiler API: **REJECT for Alpha.** The official native implementation still marks its API not
  ready. The Element compiler directly depends on the JavaScript TypeScript compiler API.
- Build integration: **DEFER.** No benefit is proven beyond faster checking.
- Deno interaction: **use Deno's supported checker for Deno source** and use external `tsc` only for
  the Node/npm consumer matrix where that consumer contract is intentional.

Delete the empty TS7 experiment directory. An experiment with no executable evidence is not a
decision record.

### Web Test Runner: ADOPT, then rename out of pilot status

Use Web Test Runner for compiled custom-element browser conformance across Chromium, Firefox, and
WebKit. Keep Deno tests for pure semantics and Playwright for document/application/navigation E2E.

The current WTR suite proves useful browser contracts, but its `pilot` task names and five tests of
WTR's own failure behavior are excessive. Retain one fail-closed configuration smoke, remove tests
that retest the upstream runner, and rename the suite to `test:element:browser`.

### CEM: ADOPT as generic metadata interchange, not as OE semantics

Use the Custom Elements Manifest analyzer/schema as the generic metadata authority for tags,
attributes, members, events, slots, and CSS parts. OpenElement may add a namespaced extension for
compiler and SSR capability, but must not maintain a second generic metadata extractor.

The current code mostly consumes and classifies CEM; the older interop harness also carries its own
validation and extraction assumptions. Replace generic validation with the upstream schema/analyzer
and keep only OpenElement's SSR admission classification.

## Upstream replacement policy

Use mature upstream tools where their contract is actually the same:

- Deno workspace tasks replace custom package task orchestration.
- `publint` owns generic package-layout validation.
- `@arethetypeswrong/cli` owns cross-resolution declaration diagnostics.
- API Extractor is the preferred future public API report once declarations are authoritative.
- Custom Elements Manifest owns generic component metadata.
- Web Test Runner owns component-level browser test execution.
- Playwright owns full document/application/browser E2E.
- npm trusted publishing, provenance, and `npm audit signatures` own registry attestation mechanics.
- Deno lockfiles own downloaded dependency integrity.

Do not adopt Changesets merely to replace 200 lines of release policy. OpenElement currently releases
one coordinated version line from four packages; Deno's workspace versioning plus a thin explicit
release admission check is smaller. Revisit only if packages gain genuinely independent versions.

### Acceptance matrix

Every public mode requires fresh install, pack/install outside the workspace, typecheck,
declarations, source maps, dependency isolation, and its applicable lifecycle commands.

- Standalone Element: compiled ESM registration, attributes/properties/events, FACE/forms,
  lifecycle, focus, composed events, Custom Element registration, and no Router dependency.
- Router Route Mode: URL/method resolution, loader/action/redirect/error/cancellation, 404, 405 with
  `Allow`, and no Element/Lit/Preact/Vite dependency.
- Native Framework Mode: dev/build/start/preview policy, SSR/SSG/request-time rendering, browser
  continuation, disabled-JS navigation/forms, back/forward, stale response suppression, disposal,
  and resource cleanup.
- Lit Framework Mode: the same application matrix independently, with no Native compiler/runtime
  dependency inferred from Native results.
- Browser execution: Chromium, Firefox, and WebKit for component conformance and applicable app E2E.
- Runtime execution: record Deno, Node, Bun, Nitro Node, and Workers per renderer/mode. `NOT RUN` is
  not `PASS`.

## Migration risks and stop conditions

### Package rename and adapter dissolution

- Breaking: yes. This is acceptable before the first 1.0 public Alpha.
- Stop if moving Vite code forces Vite/Nitro into Route Mode installation or browser declarations.
- Stop if Element must depend on Router, or if compiler host code leaks into Element's browser graph.
- Roll back the physical move, not the ownership decision; a private internal workspace package is
  preferable to a false public product.

### Generic tool replacement

- Stop unless the upstream tool is tested against Deno specifiers, generated modules, all public
  subpaths, and packed tarballs.
- Never keep both old and new production gates indefinitely. One migration change must name the
  replacement, prove equivalence, switch CI, and delete the displaced implementation.
- Do not trade 500 lines of local code for a framework plus 500 lines of configuration.

### Qualification consolidation

- Stop if consolidation removes a mode-specific assertion or turns an independent packed consumer
  into a workspace-source test.
- Shared runner utilities may be reused; fixture inputs, installs, outputs, and verdicts must remain
  independent.

### Release and provenance

- Do not publish, tag, create Releases, delete Releases, or alter dist-tags in this convergence pass.
- A new candidate SHA invalidates SHA-bound external evidence.
- npm publication continues to require trusted publishing/OIDC, provenance, exact candidate SHA,
  fresh verification, human review, and explicit maintainer approval.

## Recommended execution order

### Phase A: correct public ownership

- Goal: publish Element, Router, and Create as the durable public topology. (Implemented: the
  workspace publishes exactly `@openelement/element`, `@openelement/router`, and
  `@openelement/create`; `packages/app` and `packages/adapter-vite` are deleted.)
- Scope: App rename, Adapter Vite responsibility split, imports, exports, starters, docs, fixtures.
- Forbidden: new renderer, new bundler abstraction, or new product subsystem.
- Acceptance: Route Mode installs without Element/Vite; Element installs without Router; framework
  modes pass from packed artifacts.
- Stop: any dependency inversion or host/browser graph leak.

### Phase B: close toolchain decisions

- Goal: one compiler frontend, production WTR, CEM as generic metadata authority.
- Scope: remove empty Oxc/TS7 experiments, rename WTR out of pilot, remove duplicated CEM parsing.
- Forbidden: parallel compiler frontends or TypeScript 7 Compiler API migration.
- Acceptance: compiler, declaration, source-map, malformed-input, and browser matrices remain green.
- Stop: diagnostic/source-map or Part Program semantic drift.

### Phase C: reshape qualification as fixtures

- Goal: make executable product evidence readable and mode-owned.
- Scope: split the packed app harness; move Nitro and third-party WC sources; consolidate shared
  process/server helpers.
- Forbidden: converting packed tests to workspace-source tests.
- Acceptance: four isolated public modes and per-runtime results remain explicit.
- Stop: any lost matrix cell.

### Phase D: delete displaced infrastructure

- Goal: remove obsolete v0.44, AutoFlow, duplicated consumer, URLPatternList provenance, and unused
  helper systems.
- Dependency: Phases A-C must have named replacements and passing evidence.
- Acceptance: no active task, workflow, document, or test references a deleted path; Git retains
  history.
- Stop: a deleted check has no equivalent owner.

### Phase E: final Beta.2.3/Alpha qualification

- Goal: run the complete source, packed, browser, runtime, and security matrix on one exact SHA.
- Acceptance: no inferred passes, no stale evidence, no hidden workspace aliases.
- Stop: any required cell is failed, skipped without policy, unknown, or not run.

### Phase F: release-history decision

- Goal: separately decide the GitHub Release display policy.
- Current status: **DEFERRED by maintainer instruction; make no Release-object changes.**
- Tags, commit history, registry provenance, and evidence remain immutable regardless of the future
  display decision.

### Phase G: architecture freeze

- Goal: declare `1.0.0-alpha.1` only after independent verification and human GO.
- Acceptance: no unresolved package ownership, no parallel toolchain truth, and no unclassified core
  tool remains.
- After entry: architecture changes require evidence from an independent real application.

## Final maturity judgment

If Phases A-E and G complete with the stated evidence, OpenElement will have the architectural
maturity to enter `1.0.0-alpha.1`. It will not yet have the product maturity for 1.0 stable; that
requires real applications, migration experience, operational soak, and external consumer feedback.

At the inspected SHA the answer is **NO-GO** for architecture freeze, for three concrete reasons:

1. public package names still contradict the Element + Router doctrine;
2. tooling contains unclassified historical and duplicated systems;
3. required fresh independent verification and human release authority are not code-generated
   evidence.
